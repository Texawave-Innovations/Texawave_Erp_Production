1. Executive Overview & Notation Guide Crow's Foot Reference

Every entity, attribute, foreign key constraint, cardinality indicator, and cascade action in this specification reflects the ACTUAL, CURRENT database architecture verified directly against packages/database/prisma/schema.prisma and the PostgreSQL migrations.

Inviolable Architectural Rules
• Multi-Tenant Isolation: All 11 tables strictly reside in "finance". Every table has an organization_id foreign key referencing platform.organizations(id) with ON DELETE RESTRICT ON UPDATE CASCADE.
• Immutable Ledger Core: The GL engine (journal_entries and journal_lines) represents the single source of truth. Operational vouchers link via 1:1 foreign keys.
• Double-Entry Invariant: At all times for posted vouchers: $sum ext{debit\_amount} = sum ext{credit\_amount}$.
• Dynamic Reporting: Statements are runtime aggregations in FinancialReportsService; no stale reporting tables.
Crow's Foot Cardinality Notation
Symbol Cardinality Semantics
|| --- || 1 : 1 (Mandatory) Parent requires child, unique key on FK
|| --- o| 1 : 0..1 (Optional) Zero or one child (e.g. reversal entry)

|| --- o{ 1 : 0..* (Optional Many) Parent has zero or many children
|| .. o| Logical Reference Application-level link, no hard DB constraint

Foreign Key Deletion Rules & Constraint Keys

ON DELETE RESTRICT
Prevents accidental deletion of parent records (applied on organization_id and account_id).
ON DELETE CASCADE
Automatically cleans up child lines when parent is deleted (applied on journal_lines and bank_transactions).
ON DELETE SET NULL
Safely unlinks optional parent references without losing child voucher (applied on CRM customer, bank account, and SCM payment).

2. ER 1 — Finance Module Comprehensive Overview Complete Subsystem Ecosystem

High-level entity relationship map illustrating all 11 core Finance tables and cross-schema connections to Platform, CRM, SCM, and HR.

Architectural Subsystem Hub
• Chart of Accounts (accounts): Central 5-type ledger catalog.
• General Ledger (journal_entries & journal_lines): Transactional backbone. All operational modules write 1:1 posted vouchers.
• Multi-Tenant Anchor: platform.organizations enforces tenant boundaries across all 11 entities with RESTRICT.
Cross-Schema Integration Points
• crm.accounts: Linked to customer receipts (payments_received.customer_id).
• scm.supplier_payments: 1:1 linked to vendor disbursements (payments_made.scm_supplier_payment_id).
• hr.expense_claims: 1:1 unique logical link to employee claims (expenses.hr_expense_claim_id).

3. ER 2 — Chart of Accounts & General Ledger Double-Entry Foundation

Core double-entry accounting engine: hierarchical Chart of Accounts (COA), journal transaction vouchers, and balanced debit/credit lines.

Account Hierarchy & Invariants
• Hierarchical Tree: parent_account_id self-reference enables sub-accounts of arbitrary depth.
• Double-Entry Balance: All posted entries assert $sum ext{debits} = sum ext{credits}$.
• Audit Trail: Posted entries are immutable. Reversals create symmetric entries via reversed_entry_id.
Cascade & Integrity Actions
• journal_lines.journal_entry_id: ON DELETE CASCADE cleans up lines if draft entry is removed.
• journal_lines.account_id: ON DELETE RESTRICT prevents dropping active accounts with transaction history.
• accounts.parent_account_id: ON DELETE SET NULL safely unlinks parent without losing sub-accounts.

4. ER 3 — Banking & Treasury Reconciliation Liquid Treasury Management

Company bank account administration, statement transaction feeds, and automated/manual reconciliation against posted General Ledger vouchers.

Reconciliation Lifecycle & Invariants
• Dual Balance Architecture: Tracks physical current_balance and links to Asset GL account (gl_account_id).
• 1:1 Matching: Statement feeds match posted GL entries via matched_journal_entry_id, setting is_reconciled = true.
• Indian IFSC Validation: Validates official RBI IFSC regex format on account creation.
Cascade & Integrity Actions
• bank_transactions.bank_account_id: ON DELETE CASCADE removes statement lines if bank account is dropped.
• bank_transactions.matched_journal_entry_id: ON DELETE SET NULL disconnects GL match safely.
• bank_accounts.gl_account_id: ON DELETE SET NULL preserves bank account if GL account is re-organized.

5. ER 4 — Customer Payments Received (AR) Accounts Receivable Inflow

Customer receipt vouchers, multi-invoice breakdown allocations, CRM customer mapping, and unallocated advance funds tracking.

Receipt Workflow & Advances
• Workflow Progression: DRAFT $ o$ CONFIRMED $ o$ CANCELLED.
• Advance Credit: Unallocated receipt amounts are retained in unallocated_amount under Customer Advances.
• Line Allocations: Allocates payments across multiple sales invoice references (invoice_reference).
Automated GL Posting & SCM Link
• Posting Symmetry: Confirming receipt generates 1:1 Journal Entry: DR Bank Account (1100), CR Accounts Receivable (1200).
• customer_id: References crm.accounts with ON DELETE SET NULL, preserving historical receipt identity.
• payment_received_allocations: ON DELETE CASCADE cleanly removes allocation lines if draft receipt is deleted.

6. ER 5 — Payments Made & SCM Integration (AP) Accounts Payable Outflow

Vendor disbursements, bank account deductions, automated General Ledger postings, and direct 1:1 foreign key linkage to SCM supplier payments.

Procure-to-Pay Integration
• 1:1 SCM Pairing: scm_supplier_payment_id has an explicit unique key constraint preventing duplicate disbursement vouchers.
• SCM Cascade: Links backward to scm.supplier_bills and scm.suppliers.
• Disbursement Immutability: Confirmed payments cannot be modified; cancellation posts a reversal voucher.
Treasury Impact & Posting Symmetry
• Bank Balance Deduction: Confirmation decrements current_balance atomically on target bank account.
• GL Voucher: Generates 1:1 Journal Entry: DR Accounts Payable (2000), CR Bank Account (1100).
• bank_account_id & scm_supplier_payment_id: ON DELETE SET NULL preserves financial voucher.

8. ER 7 — GST & Input Tax Credit Registry Statutory Tax Compliance

Central GST repository used for filing monthly returns (GSTR-1, GSTR-3B) and tracking statutory tax liabilities and Input Tax Credit claims.

Return Period & Supply Types
• Period Organization: Partitioned by period (YYYY-MM) and entry_type (OUTWARD, INWARD, REVERSE_CHARGE).
• Tax Splits: Discrete columns for cgst_amount, sgst_amount, igst_amount, cess_amount, and computed total_tax.
• GSTR-3B Net Liability: Net tax payable = Outward Tax - Eligible Inward ITC.
Polymorphic Source References
• Composite Pointers: source_reference stores typed references (e.g. EXPENSE:12, PURCHASE_BILL:45, SALES_INVOICE:501).
• Lookup Index: Composite index on (organization_id, source_reference) accelerates invoice reconciliation during audit filings.
• organization_id: Enforces strict tenant separation with RESTRICT.

9. ER 8 — Financial Reporting Underlying Tables Dynamic Runtime Aggregations

Architectural model confirming that Financial Reports (Balance Sheet, P&L, Trial Balance, General Ledger, Cash/Bank Summary) do not use static reporting tables, but are calculated dynamically by FinancialReportsService.

Physical Base Tables Queried
• finance.accounts: Chart of Accounts hierarchy, account types (ASSET, LIABILITY, EQUITY, REVENUE, EXPENSE).
• finance.journal_entries & journal_lines: Transaction lines filtered strictly by status = 'POSTED' and date range.
• finance.bank_accounts: Current liquid balances and movements.
Dynamic Statement Computations
• Trial Balance: Verifies zero-sum integrity ($sum ext{Debits} = sum ext{Credits}$).
• Balance Sheet: Groups by account type: $ ext{Assets} = ext{Liabilities} + ext{Equity}$. Retained earnings dynamically injected from P&L.
• Profit & Loss: Operating Revenue minus Operating Expenses = Net Profit.

12. Discrepancies, Gaps & Architectural Recommendations Action Items for Engineering

Findings and architectural recommendations submitted based on schema inspection and migration verification.

1. Dedicated Sales Invoicing Table
• Current State: Customer receipts allocate funds via invoice_reference: String without a foreign key to a dedicated sales.invoices table.
• Impact: String references allow flexibility but lack database-layer foreign key validation.
• Recommendation: Implement a dedicated finance.sales_invoices table and add an optional foreign key in payment_received_allocations.
2. Local PostgreSQL Container Status
• Current State: Local container on port 5432 is stopped (EACCES / P1001).
• Impact: All definitions verified from migration DDL with 100% parity. Live verification is staged.
• Action: Start PostgreSQL (docker compose up -d db) and run npx prisma migrate status.
3. Cross-Schema Foreign Key Dependencies
• Current State: The finance schema contains physical foreign keys to platform, crm, and scm.
• Schema Split Roadmap: If schemas are split into independent databases in the future, these foreign keys will transition to event-driven logical UUID references.
4. High-Volume Index Optimization
• Current State: 13 unique constraints and 20 secondary indexes cover standard tenant and date queries.
• Recommendation: Add composite index on finance.journal_lines(organization_id, account_id, created_at) as ledger volume exceeds 500k rows.
